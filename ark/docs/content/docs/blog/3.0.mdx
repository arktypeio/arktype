Your definitions don't change- just where they run. **ArkType (dynamic)** parses them at runtime with no build step, like always. **ArkType (precompiled)** builds each one when you build, so your bundle gets a validator with only the checks your types need. No parser, and no code generated at runtime. <Claim id="buildChoice" />

```ts
// ---cut-start---
declare const data: unknown
// ---cut-end---

export const User = type({
	name: "string > 0",
	email: "string.email",
	"age?": "number.integer >= 0"
})

const out = User(data)

if (out instanceof type.errors) console.error(out.summary)
```

## `@ark/aot`

[`@ark/aot`](/docs/precompile) is a plugin for the bundler you already run: Vite, Rollup, Rolldown, webpack, Rspack, esbuild, Bun or Farm, and Vitest runs tests through it. Drivers cover Node, Bun's runtime and Next's Turbopack.

```ts title="vite.config.ts"
import { precompile } from "@ark/aot/unplugin"

export default {
	plugins: [precompile.vite()]
}
```

Your definitions don't change. Each Type your program defines becomes a validator on `arktype/runtime` that validates, asserts and implements Standard Schema as the Type did, so code that calls it doesn't change either. Scopes, Modules, Generics, cyclic Types, `match` and `type.fn` precompile too.

A definition the build can't precompile, like one built from a value known only at runtime, fails the build with its file, line, reason and fix:

```
src/forms.ts:14:19  type(`string <= ${limit}`) cannot be precompiled
  `limit` is a parameter of makeField (src/forms.ts:12:22); its value is known only at runtime
  Standalone builds construct every Type at build time. Make it static, or build with runtime: "arktype".
```

`npx arktype-precompile --check "src/**/*.ts"` lists every such definition before you switch, and `runtime: "arktype"` precompiles what it can while shipping arktype for the rest, so you can migrate a program at your own pace. [Setup](/docs/precompile/setup) has a config for each bundler.

Options go in the plugin call or in an [`ark.json`](/docs/precompile/options#arkjson) that the plugin, the drivers, the CLI and the ESLint rule all read, and a [preset](/docs/precompile/options#presets) sets several at once: `"smallest"` trades speed for size. A production build leaves out the runtime checks of what the build already verified.

### Set theory at build time

ArkType reduces every definition to a normalized set of constraints, so it knows which Types overlap, which are subtypes of others and which can never both be satisfied. Precompiled, all of that happens in your build:

- **Unions discriminate themselves.** ArkType finds the key that tells a union's branches apart and switches on it, so data is checked against one branch rather than each in turn, and a branch never rechecks the key it was chosen by. You never declare a discriminator.
- **Redundant checks disappear.** `number > 0` intersected with `number >= 10` is one check, `number >= 10`. Divisible by 2 and by 3 is divisible by 6.
- **Contradictions never ship.** `{ id: string }` intersected with `{ id: number }` throws a ParseError, which fails the build rather than shipping a validator that rejects everything.

```ts
const Shape = type({
	kind: "'circle'",
	radius: "number > 0"
}).or({
	kind: "'square'",
	side: "number > 0"
})

const Six = type("number % 2 & number % 3")

Six.expression // "number % 6"
```

Precompiled, `Shape` checks data like this, its helpers inlined: one `switch` on `kind`, each case checking only the key that's left:

```js
// @noErrors
// ---cut---
data => {
	switch (data?.kind) {
		case "circle":
			return Number.isFinite(data.radius) && data.radius > 0
		case "square":
			return Number.isFinite(data.side) && data.side > 0
	}
	return false
}
```

ArkType isn't the first validator to compile. typia also generates checks from your TypeScript types at build time, and it specializes some unions. The difference is that ArkType brings a type system of its own to the build, so your definitions are reduced, intersected and discriminated before any code is written.

## Optimized for agentic dev

Build steps used to cost you attention. If an agent runs your local dev, a build step is just one more loop it's already good at- build, read the error, fix, rebuild. So we made sure every message along the way names the fix:

- **Definitions** are checked by `tsc` as you write them, and a typo's error is the type the string was checked against, like `"number | strin"` against `"number | string"`.
- **The build** reports what it can't precompile with the file, line, reason and fix. [Troubleshooting](/docs/precompile/troubleshooting) quotes each message, and [shadow mode](/docs/precompile/advanced#shadow-mode) fails a test wherever a precompiled validator would behave otherwise than arktype.
- **Validation** returns errors that say where, what was expected and, for a dynamic Type, what arrived, ready to hand back to a model as a tool result.

Set it up once:

```bash
npx skills add arktypeio/arktype
```

The [skill](/docs/agents#skill) teaches an agent current syntax, how it maps to TypeScript, the mistakes to avoid and how to work in a precompiled project. Every docs page is also Markdown at its URL plus `.md`, and [/llms.txt](https://arktype.io/llms.txt) indexes them. See [Agents](/docs/agents).

## `codec` and `.encode`

`codec` pairs a morph with its inverse, so output can be encoded back into input. Every Type has `.encode`, which inverts each of its morphs, so a codec encodes wherever it's nested:

```ts
import { codec } from "arktype/codecs"

const EpochMs = codec("number.integer", "Date", {
	decode: n => new Date(n),
	encode: d => d.getTime()
})

const Event = type({ name: "string", at: EpochMs })

// { name: "launch", at: new Date(0) }
const event = Event({ name: "launch", at: 0 })
// { name: "launch", at: 0 }
const encoded = Event.encode(event)
```

Parse keywords like `string.date.iso.parse` encode back to strings. `arktype/codecs` installs encoding when imported, so an app that doesn't encode doesn't ship it. Codecs and `.encode` [precompile](/docs/codecs#precompiling) like any other definition. See [Codecs](/docs/codecs).

## Error messages in other languages

Configure a locale to write error messages in another language. ArkType ships `en` and `de`, and a locale is an object you can spread, extend or write from scratch, including one that calls an i18n library:

```ts title="config.ts"
import { configure } from "arktype/config"
import { de } from "arktype/locales/de"

configure({ locale: de })
```

`locale` can also be a function, called when an `ArkErrors`' messages are first read, so errors follow the language of the request that reads them. See [i18n](/docs/i18n).

## Fewer errors, and transforms in place

`errors` returns less when you need less: `"first"` stops at the first error validation finds, and `"none"` returns one error saying the data is invalid. `mutatesInput` writes what a Type transforms into its input instead of copying it. Each is installed by its own import, so a program that doesn't choose one doesn't ship it:

```ts title="config.ts"
import { configure } from "arktype/config"
import "arktype/errors"

configure({ errors: "first" })
```

A precompiled build takes both as options, alongside [`members`](/docs/precompile/options#members), which drops what a validator has besides validating, and [`optimize: "size"`](/docs/precompile/options#optimize-and-optimizeerrors). See [Configuration](/docs/configuration#errors).

## Dynamic Types do less work

A Type compiles when it's first used rather than when it's defined, so a Type a program never calls costs nothing to compile. A Type that calls no narrow or morph finds its errors' issues only when they're first read, so rejecting data costs little more than the check that rejected it. <Claim id="strictSpeedup" />

## Syntax

[`!=`](/docs/primitives#number-ranges) excludes one value, like `number != 0`, and a union of ranges merges where it can: `1 < number < 10 | 10 <= number < 100` is `1 < number < 100`, and `number < 0 | number > 0` is `number != 0`. An object's [`"@"`](/docs/expressions#meta) key holds its description or meta, as `"@"` does in a tuple expression:

```ts
const User = type({
	"@": "a user",
	name: "string"
})

// ArkErrors: must be a user (was a number)
User(5)
```

## ArkSets and JSON Schema

[ArkSets](/docs/sets) applies the same set theory to any schema: a Type, a Standard JSON Schema like Zod's, or a plain JSON Schema. `isSubset(v1, v2)` tells you whether a new version of an API schema still accepts everything the old one did, and `intersect`, `union` and `toJsonSchema` combine and normalize schemas across formats.

`jsonSchemaToType` from [`@ark/json-schema`](/docs/json-schema/from-json-schema) reads a schema through it, so the Type accepts exactly what a JSON Schema 2020-12 validator does, and infers the type of a schema written in the call.

## Errors as data

An `ArkErrors`' `issues` are plain objects, discriminated by `code`, with the keys their JSON has. `flatByPath` and `flatProblemsByPath` are functions `arktype` exports. Errors print an object by its kind, like `(was an object)`, so an object never grows a message or leaks what it holds into a log, and undeclared keys and union misses have codes of their own, `undeclared` and `discriminant`. [Upgrading](/docs/upgrading) lists each change with what to write instead.
