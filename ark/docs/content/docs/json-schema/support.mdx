---
title: Keyword support
description: How fromJsonSchema reads each JSON Schema keyword, which ones throw, and which are only annotations.
---

A Type read from a schema by [`fromJsonSchema`](/docs/json-schema/from-json-schema), directly or as a Standard Schema's JSON Schema, accepts exactly what a JSON Schema 2020-12 validator accepts, except that lengths count UTF-16 code units, with ajv as the tiebreaker. Each keyword is read in one of five ways:

- **supported**: the Type checks it, and [comparisons](/docs/json-schema/compare) like `.extends()` reason about it.
- **opaque**: the Type checks it exactly, with a predicate. Comparisons through it can't be proven, and `toJsonSchema()` needs a [`predicate` fallback](/docs/json-schema/to-json-schema#fallback-codes) to write it back.
- **annotation**: kept as the Type's metadata, and not validated.
- **throws**: reading the schema throws a `ParseError` naming the keyword's JSON Pointer.
- **ignored**: has no effect.

Every keyword in a schema applies, and a type's keywords constrain only that type while leaving the other JSON types unconstrained: `{ minimum: 5 }` accepts `"foo"` and other JSON values like `null` or `{}`, rejects `-1` and non-JSON values like `undefined`, `bigint`, `symbol`, or functions, and `{ type: ["string", "number"], minLength: 2 }` accepts `3` but not `"a"`.

[`configure()`](/docs/configuration) doesn't change what a schema accepts: whatever `onUndeclaredKey`, `exactOptionalPropertyTypes`, `numberAllowsNaN` and `numberAllowsInfinity` say, an object allows keys it doesn't declare, an optional property can't be `undefined`, and a number is finite.

A keyword with an invalid value throws, like `#/minLength must be a non-negative integer (was -1)`. A keyword JSON Schema doesn't define is ignored.

Of OpenAPI 3.0's own forms, which `toJsonSchema({ target: "openapi-3.0" })` writes, only `nullable` is read: beside a `type`, `nullable: true` adds `null` to that type as ajv reads it, so a sibling `enum` must list `null` too; without a `type` — beside `allOf`, `anyOf`, `oneOf`, `$ref`, `enum`, `const`, or any other subschema — `nullable: true` unions the schema with `null`. `example` is ignored, and a boolean `exclusiveMinimum` throws.

`fromJsonSchema` checks a schema written in the call as you write it: an invalid keyword value is a type error, as is each keyword below that throws, except a `$ref` to another document. See [Invalid schemas](/docs/json-schema/from-json-schema#invalid-schemas).

## Core

| keyword                                                     | support     | notes                                                                                                                         |
| ----------------------------------------------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `true`, `false`                                             | supported   | `unknown` and `never`                                                                                                         |
| `type`                                                      | supported   | a name or an array of names. `"object"` excludes arrays and functions                                                         |
| `const`, `enum`                                             | supported   | objects and arrays are compared by value                                                                                      |
| `$ref`                                                      | supported   | `#`, a JSON Pointer like `#/$defs/Node`, an anchor or an embedded `$id`, including recursive refs                             |
| `$ref` to another document                                  | **throws**  | only refs into the same document are resolved                                                                                 |
| `$defs`, `definitions`                                      | supported   | read where a `$ref` points to them. Each value must be a schema                                                               |
| `$dynamicRef`, `$recursiveRef`                              | **throws**  | ignored under a draft-07 or earlier `$schema`, which has neither                                                              |
| `title`, `description`, `default`, `examples`, `deprecated` | annotation  | `default` is not applied                                                                                                      |
| `$schema`                                                   | annotation  | draft-07 or earlier ignores the keywords beside a `$ref`, as those drafts do                                                  |
| `$id`, `$anchor`, `$dynamicAnchor`                          | supported   | identify a schema a `$ref` resolves to. Draft-04 reads `id`                                                                   |
| `$comment`, `readOnly`, `writeOnly`                         | **ignored** |                                                                                                                               |
| `contentEncoding`, `contentMediaType`                       | **ignored** | annotations in 2020-12                                                                                                        |
| `nullable` (OpenAPI 3.0)                                    | supported   | adds `null` to the `type` beside it, or unions the schema with `null` without a `type`. **Throws** if `false` beside `"null"` |

## Composition

| keyword              | support   | notes                                                           |
| -------------------- | --------- | --------------------------------------------------------------- |
| `allOf`, `anyOf`     | supported |                                                                 |
| `oneOf`              | supported | when its branches are disjoint, it's a union. Otherwise, opaque |
| `not`                | opaque    |                                                                 |
| `if`, `then`, `else` | opaque    | `if` without `then` or `else` has no effect                     |

Composition keywords apply together and beside any other keyword:

```ts
import { fromJsonSchema } from "arktype"

const T = fromJsonSchema({
	anyOf: [{ type: "string" }, { type: "number" }],
	not: { const: 0 }
})

T.allows("a") // true
// ArkErrors: must be other than 0
T(0)
```

## Strings

| keyword                  | support    | notes                                                                                  |
| ------------------------ | ---------- | -------------------------------------------------------------------------------------- |
| `minLength`, `maxLength` | supported  | counts UTF-16 code units, as arktype's bounds do, where JSON Schema counts code points |
| `pattern`                | supported  | a string, or a `RegExp` read with its own flags                                        |
| `format`                 | annotation | as the spec defaults to, and as `toJsonSchema()` writes it                             |

## Numbers

| keyword                                | support   | notes                                         |
| -------------------------------------- | --------- | --------------------------------------------- |
| `minimum`, `maximum`                   | supported |                                               |
| `exclusiveMinimum`, `exclusiveMaximum` | supported | a number. Draft 4's boolean form throws       |
| `multipleOf`                           | supported | an integer. Any other positive number, opaque |

## Arrays

| keyword                                  | support    | notes                                                                                                      |
| ---------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------- |
| `prefixItems`, `items`                   | supported  | prefix elements are optional, as JSON Schema says: `[string?, number?, ...unknown[]]`. `items` is the rest |
| `items` as an array, `additionalItems`   | supported  | draft-07's tuples                                                                                          |
| `minItems`, `maxItems`                   | supported  |                                                                                                            |
| `uniqueItems`                            | opaque     | items are compared as JSON values                                                                          |
| `contains`, `minContains`, `maxContains` | opaque     | `minContains: 0` without `maxContains` has no effect                                                       |
| `unevaluatedItems`                       | **throws** | ignored under a draft-07 or earlier `$schema`, which has no such keyword                                   |

## Objects

| keyword                                                 | support    | notes                                                                                           |
| ------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------- |
| `properties`, `required`                                | supported  | a `required` key not in `properties` must be present, with any value. See below                 |
| `patternProperties`                                     | supported  |                                                                                                 |
| `additionalProperties`                                  | supported  | `false` rejects other keys. A schema is an index signature alone, or opaque beside `properties` |
| `propertyNames`, `minProperties`, `maxProperties`       | opaque     | one every object meets, like `propertyNames: { type: "string" }`, has no effect                 |
| `dependentRequired`, `dependentSchemas`, `dependencies` | opaque     | one every object meets, like `dependentRequired: { a: [] }`, has no effect                      |
| `unevaluatedProperties`                                 | **throws** | ignored under a draft-07 or earlier `$schema`, which has no such keyword                        |

A JSON object's properties are its own, so `required: ["toString"]` rejects `{}`, though `{}` inherits `toString` from `Object.prototype`. A property named by a key `Object.prototype` has is read as a pattern that matches only that key, which, unlike a property, checks an own key alone:

```ts
import { fromJsonSchema } from "arktype"

const T = fromJsonSchema({
	type: "object",
	properties: { toString: { type: "string" } }
})

T.expression // "{ [/^toString$/]: string } & isNonArray"
T.allows({}) // true
```
