---
title: From JSON Schema
description: Read a JSON Schema, or a Standard JSON Schema like a Zod schema, into a Type with fromJsonSchema, and infer its type.
---

`fromJsonSchema` reads a JSON Schema into a Type:

```ts
import { fromJsonSchema } from "arktype"

const User = fromJsonSchema({
	type: "object",
	properties: {
		name: { type: "string" },
		age: { type: "integer", minimum: 0 }
	},
	required: ["name"]
})

User.expression // "{ name: string, age?: number % 1 >= 0 } & isNonArray"
User({ name: "Ada" }) // { name: "Ada" }
// ArkErrors: age must be an integer
User({ name: "Ada", age: 1.5 })
```

`true` reads as `unknown` and `false` as `never`. The result is a Type like any other, so it validates, composes into definitions and [compares](/docs/json-schema/compare) with Types, other JSON Schemas and schemas from other libraries.

## What it reads

`fromJsonSchema` takes one of:

- a **JSON Schema**: an object or a boolean, read as [Keyword support](/docs/json-schema/support) describes.
- a **[Standard JSON Schema](https://standardschema.dev/json-schema)**: a schema whose `~standard` has `jsonSchema`, like one from Zod 4.2.0 or later, read as the draft 2020-12 JSON Schema of its input, so what that can't express, like Zod's refinements, transforms and `undefined`, is left out. An arktype Type is read as its own input directly, keeping non-JSON domains like `Date` and narrows; pass `T.toJsonSchema()` to read it by JSON Schema's rules. Pass any other library's schema as its JSON Schema, like `z.toJSONSchema(schema)` before Zod 4.2.0.

```ts
import { fromJsonSchema } from "arktype"
import { z } from "zod"

const User = fromJsonSchema(z.object({ name: z.string(), age: z.number() }))

User.expression // "{ age: number, name: string } & isNonArray"
```

Anything else throws a `ParseError`, as does a Standard Schema without `~standard.jsonSchema`, which is also a type error, and one whose `~standard.jsonSchema` throws, like Zod's for `z.date()`, with the library's error as its `cause`.

An object meant as neither, like the definition `{ name: "string" }`, reads today as a JSON Schema whose keywords are all unknown, which accepts everything, so `fromJsonSchema({ name: "string" })` is `unknown`; what such an object means is unspecified, and a minor release may throw for it.

## Inferring its type

`fromJsonSchema` infers the type of a JSON Schema written in the call, or declared `as const`:

```ts
import { fromJsonSchema } from "arktype"

const User = fromJsonSchema({
	type: "object",
	properties: {
		name: { type: "string" },
		tags: { type: "array", items: { type: "string" } }
	},
	required: ["name"]
})

// { name: string; tags?: string[] }
type User = typeof User.infer
```

The inferred type never rejects a value the schema accepts, but it can be wider: constraints like `minimum` and `pattern` don't narrow it, and a `$ref` that isn't a JSON Pointer, like one to an anchor, infers `unknown`. Inference follows `$ref`s into `$defs`, `definitions` and OpenAPI `components.schemas`, including recursive ones, and composition, `if`/`then`/`else` and `not`.

A Standard Schema infers its input, as `StandardSchemaV1.InferInput` does. A JSON Schema TypeScript can't see as a literal, like one parsed from a `.json` file, infers `unknown`. If you know its shape, annotate the result:

```ts
import { fromJsonSchema, type Type } from "arktype"
declare const userJson: object
// ---cut---
const User: Type<{ name: string }> = fromJsonSchema(userJson) as never

// { name: string }
const user = User.assert({ name: "Ada" })
```

The annotation isn't checked against the schema, so keep the two in sync yourself.

## How it reads JSON Schema

A Type read from a JSON Schema accepts exactly what a JSON Schema 2020-12 validator accepts, except that lengths count UTF-16 code units, with ajv as the tiebreaker. Every keyword in a schema applies, local `$ref`s resolve, including recursive ones, and draft-07 forms like `items` arrays and `definitions` are read too:

```ts
import { fromJsonSchema } from "arktype"

const Tree = fromJsonSchema({
	$defs: {
		Node: {
			type: "object",
			properties: {
				value: { type: "number" },
				children: { type: "array", items: { $ref: "#/$defs/Node" } }
			},
			required: ["value"]
		}
	},
	$ref: "#/$defs/Node"
})

Tree.allows({ value: 1, children: [{ value: 2 }] }) // true
```

A `$ref` resolves against the schema it's in, so to read a schema from an OpenAPI document, spread the document into a schema that refers to it:

```ts
import { fromJsonSchema } from "arktype"

const openApi = {
	openapi: "3.1.0",
	components: {
		schemas: {
			User: {
				type: "object",
				properties: { name: { type: "string" } },
				required: ["name"]
			}
		}
	}
} as const

const User = fromJsonSchema({ ...openApi, $ref: "#/components/schemas/User" })

User.allows({ name: "Ada" }) // true
```

OpenAPI 3.0's `nullable: true` adds `null` to the `type` beside it, as ajv reads it, and infers it there too. A `nullable` without a `type`, like one beside a `$ref`, throws a `ParseError`, as ajv does.

A schema's `description` is kept on `T.description` and metadata so it round-trips through `toJsonSchema()`, without replacing validation error `expected` phrasing.

[Keyword support](/docs/json-schema/support) lists how each keyword is read. `fromJsonSchema` prevents code injection and prototype pollution, so a schema can't run arbitrary code, but it compiles `pattern` and `patternProperties` with JavaScript's `RegExp` and intersects `allOf` branches eagerly: don't pass untrusted regexes that can backtrack catastrophically or deeply nested `allOf` combinations without bounding the input.

## Invalid schemas

A JSON Schema written in the call is checked as you write it:

```ts
// @errors: 2322
import { fromJsonSchema } from "arktype"
// ---cut---
// TypeScript: minLength must be a non-negative integer (was -1)
fromJsonSchema({ type: "string", minLength: -1 })

// TypeScript: unevaluatedProperties isn't supported by fromJsonSchema
fromJsonSchema({ type: "object", unevaluatedProperties: false })
```

`fromJsonSchema` throws a `ParseError` naming the keyword's JSON Pointer for an invalid keyword TypeScript can't check, like a `pattern`, or one it can't read exactly, like a `$ref` to another document:

```ts
import { fromJsonSchema } from "arktype"
// ---cut---
// ParseError: #/pattern must be a valid pattern (was "[")
fromJsonSchema({ type: "string", pattern: "[" })

// ParseError: #/$ref must reference a schema in its own document (was https://example.com/user.json)
fromJsonSchema({ $ref: "https://example.com/user.json" })
```

Of the keywords it can't read, `$dynamicRef`, `$recursiveRef`, `unevaluatedItems`, `unevaluatedProperties` and a draft-04 boolean `exclusiveMinimum` or `exclusiveMaximum` are type errors too.

One check is deliberately stricter than JSON Schema: a `required` key a schema's own `properties` don't declare is a type error where nothing else could declare it. That's a schema with no `patternProperties`, composition keyword, `$ref` or dependent schema, whose `additionalProperties` is absent or `false`, reached from the root only through the `properties`, `additionalProperties`, `items` or `prefixItems` of schemas like it. JSON Schema reads the key as required with any value, but it's usually a typo.

## Typing a schema

To check a schema you declare separately without reading it, use `JsonSchema` from `arktype`:

```ts
import type { JsonSchema } from "arktype"

const Age = {
	type: "integer",
	minimum: 0
} satisfies JsonSchema.Numeric
```

## Back to JSON Schema

A Type from `fromJsonSchema` has [`toJsonSchema()`](/docs/json-schema/to-json-schema) like any other, so reading a schema and writing it back normalizes it. Keywords [Keyword support](/docs/json-schema/support) lists as opaque, like `uniqueItems`, `not` and `if`, come back as [`predicate` fallbacks](/docs/json-schema/to-json-schema#fallback-codes), so `toJsonSchema()` throws for them unless you handle that code.
