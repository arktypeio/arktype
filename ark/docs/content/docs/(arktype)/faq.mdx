## Why do I see type errors in an ArkType package in `node_modules`?

This can occur due to incompatibilities between your `tsconfig.json` and ours. It is harmless as long as your types are correct in source.

We recommend enabling [`skipLibCheck`](https://www.typescriptlang.org/tsconfig/#skipLibCheck) in every TypeScript project to avoid false positives like this and improve editor performance.

## Why does `number` reject `Infinity`?

`number` excludes `NaN`, `Infinity` and `-Infinity` by default, so validated numbers are finite. JSON can't represent them either: `JSON.stringify(Infinity)` is `"null"`. To allow them in one type, add the corresponding keyword:

```ts
const Bound = type("number | number.Infinity | number.NegativeInfinity")
```

To allow them everywhere, configure `numberAllowsInfinity` or `numberAllowsNaN` (see [Configuration](/docs/configuration)).

## Why can't I index `ArkErrors` like an array?

`ArkErrors` isn't an `Array`. Its errors are in `issues`, one for each check that failed:

```ts
const out = type({ name: "string" })({})

if (out instanceof type.errors) {
	// the error at name
	out.issues[0]
	// ["must be a string (was missing)"]
	out.issues.map(e => e.message)
	for (const error of out.issues) console.log(error.path)
}
```

See [Errors](/docs/errors) for everything an error carries.

## Why does my error say `must be Enter a valid email`?

A string passed to `.describe()`, `ctx.reject()` or `ctx.mustBe()`, or configured as `expected`, is what the value must be, so ArkType writes "must be" before it. A whole sentence is a [`message`](/docs/configuration#message):

```ts
const Email = type("string.email").configure({ message: "Enter a valid email" })

const Zip = type("string").narrow(
	(s, ctx) =>
		/^\d{5}$/.test(s) || ctx.reject({ message: "Enter a 5-digit zip" })
)
```

## Why does my optional key reject `undefined`?

An optional key may be missing, but a key that's present must hold a value its definition allows, as with TypeScript's `exactOptionalPropertyTypes`. Add `| undefined` to the value, or set [`exactOptionalPropertyTypes: false`](/docs/configuration#exactoptionalpropertytypes) to accept `undefined` at every optional key, as Zod does.

## Why isn't my configuration applied?

Global config is fixed when the first Type is created, by a definition or by reading a keyword like `type.number`. Calling `configure` after that throws a `ParseError`: `configure() must be called before any Type is created, so import the module calling it before any module that creates one`. Put it in its own file. See [Configuration](/docs/configuration).

## Why does Jest say `Must use import to load ES Module`?

ArkType and its dependencies ship ES modules only, and Jest runs tests as CommonJS, so a test that imports arktype fails, naming `node_modules/arktype/out/index.js`. Have Jest transform those packages, with a transform that reads JavaScript, like ts-jest's `js-with-ts` preset:

```js title="jest.config.js"
module.exports = {
	preset: "ts-jest/presets/js-with-ts",
	// arktype and its dependencies ship ES modules only
	transformIgnorePatterns: [
		"/node_modules/(?!(\\.pnpm|arktype|arkregex|arksets|@ark)/)"
	]
}
```

`\\.pnpm` is for pnpm's layout, where each package is under `node_modules/.pnpm`. On Node 24.9 or later, a Jest that can `require` an ES module, like 30.5, needs no transform: run it with `NODE_OPTIONS=--experimental-vm-modules`.

## Does a morph change my input?

Only if you mutate it, or configure [`mutatesInput`](/docs/configuration#mutatesinput). A morph receives the validated value itself, not a copy, so mutating its argument mutates the caller's data. Return a new value instead:

```ts
const addTag = type({ tags: "string[]" }).pipe(o => ({
	...o,
	tags: [...o.tags, "new"]
}))
```

## Should I precompile?

If your app is bundled, yes. A [precompiled](/docs/precompile) build ships each Type as a standalone validator, without arktype's parser and without generating code at runtime, and your definitions don't change. Stay dynamic where there's no build step or a program composes Types at runtime. See [Dynamic vs Precompiled](/docs/precompile/dynamic-vs-precompiled).

## Can I get error messages in another language?

Yes. ArkType ships English and German, and you can write a locale for any other language. See [i18n](/docs/i18n).

## How does ArkType compare to Zod or Valibot?

All three validate at runtime and infer TypeScript types. The main difference is how you write a definition: ArkType uses TypeScript's own syntax, while Zod and Valibot use function calls.

```ts
// z.object({ name: z.string(), age: z.number().int().min(0).optional() })
const User = type({
	name: "string",
	"age?": "number.integer >= 0"
})
```

That means dynamic ArkType parses your definitions at runtime, so it ships a parser, and its bundle is larger than Zod's or Valibot's. [Precompiled](/docs/precompile), it ships no parser. <Claim id="loginSize" />

Coming from Zod, most APIs have a direct equivalent:

| Zod                           | ArkType                                                              |
| ----------------------------- | -------------------------------------------------------------------- |
| `z.object({ ... })`           | `type({ ... })`                                                      |
| `.optional()` on a property   | `"key?": ...`                                                        |
| `.default(value)`             | `"number = 0"` as a property value                                   |
| `z.enum(["a", "b"])`          | `"'a' \| 'b'"`                                                       |
| `z.array(T)`                  | `T.array()` or `"string[]"`                                          |
| `z.infer<typeof T>`           | `typeof T.infer`                                                     |
| `T.parse(data)`               | `T.assert(data)`                                                     |
| `T.safeParse(data)`           | `T(data)`, then `instanceof type.errors`                             |
| `.min(1, "Name is required")` | `["string >= 1", "@", { message: "Name is required" }]`              |
| `.refine(fn, "Message")`      | `.narrow((v, ctx) => fn(v) \|\| ctx.reject({ message: "Message" }))` |
| `.transform(fn)`              | `.pipe(fn)`                                                          |

[Migrating](/docs/migrating) maps the rest of Zod's API, and Valibot's, and has a prompt that migrates a project for you.

All three implement [Standard Schema](/docs/standard-schema), so a library that accepts one of them accepts the others, and you can [adopt ArkType one schema at a time](/docs/migrating#adopt-incrementally).

## Why isn't my wrapper generic working?

TypeScript's generic inference has many edge cases. General patterns for wrapping Types and definitions are outlined [in the Generics docs](/docs/generics#external).

<Callout type="info" title="Type-level logic needs a cast">

When implementing a function with a generic return type, you will almost always need to cast in your implementation, either explicitly via `as` or by using an overload.

Think of it as trading internal safety for external precision. As long as the function you're writing will be called many times externally, the overhead is justified. If not, it may not need to be generic at all. A broad return type like `string` as opposed to `${prefix}.${key}` may be sufficient.

<details>
	<summary>See an example</summary>

```ts
// via explicit cast
const createBox = <const def>(
	of: type.validate<def>
): type.instantiate<{ box: def }> =>
	type.raw({
		box: of
		// when implementing generics, never is your go-to
		// for allowing an arbitrary assignment with less risk than `any`
	}) as never

// via overloads
// only the external signatures are considered on invocation
function createBox2<const def>(
	of: type.validate<def>
): type.instantiate<{ box: def }>
// the signature associated with the implementation is much looser and should
// be thought of as equivalent to casting in terms of type safety
function createBox2(of: unknown) {
	return type.raw({
		box: of
	})
}

// Type<{ box: string }>
const Box = createBox("string")
```

In both cases, we've explicitly annotated the return type we want and used some method of casting internally to allow our implementation. This is a common pattern for implementing generic functions and, more generally, associating an implementation with typings TS can't infer on its own.

</details>

</Callout>

How a generic of your own infers depends on TypeScript rather than on ArkType's API. For anything these patterns don't cover, ask [in our Discord](https://arktype.io/discord).

## What's up with your type/Type casing?

These docs use PascalCase for some Types and camelCase for others:

```ts
const User = type({
	name: "string",
	platform: "'android' | 'ios'",
	"version?": "number | string"
})

const parseJson = type("string.json.parse").to({
	name: "string",
	version: "string.semver"
})
```

Types that only validate are named like TypeScript types. Types that transform their input behave like functions, so they're named like functions. Casing doesn't affect your Types or scope aliases, so use whatever rules suit your repo.

## Is there a way to create an async morph?

No. A morph can return a promise as its output, but ArkType doesn't await it, so run async checks after validation. If you have a use case for more, add it to [this GitHub issue](https://github.com/arktypeio/arktype/issues/462).
