## Levels

Config can be set at three levels. A more specific level overrides a broader one.

### Global

Call `configure` in its own file, and import that file before anything creates a Type:

```ts title="config.ts"
import { configure } from "arktype/config"

configure({ numberAllowsNaN: true })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

// true
type.number.allows(Number.NaN)
```

<Callout type="warn" title="Configure before any Type is created">
	Global config is fixed when the first Type is created, whether by a definition
	or by referencing a keyword like `type.number`, and calling `configure` after
	that throws unless it changes nothing, as when a test runner resets its
	modules and the config file runs again. Importing `"arktype"` first is fine,
	and `configure` can be imported from either `"arktype"` or `"arktype/config"`.
</Callout>

Global config belongs to the app. A package others install shouldn't call `configure`: it would change the app's own Types, or throw there if the app created one first. Give a package's Types their options in a [scope](#scope) or in [each Type](#type).

If your `package.json` sets `"sideEffects": false`, a bundler leaves out an import made only for its side effects, so the bundle runs without your config. List the file there instead: `"sideEffects": ["./src/config.ts"]`.

### Scope

Pass config as the second argument to `scope` or `type.module`. It applies to every Type parsed in that scope:

```ts
const $ = scope(
	{ User: { age: "number < 100" } },
	{ max: { actual: () => "unacceptably large" } }
)

// ArkErrors: age must be less than 100 (was unacceptably large)
$.export().User({ age: 101 })

// ArkErrors: age must be at most 100 (was unacceptably large)
$.type({ age: "number <= 100" })({ age: 101 })
```

### Type

`.configure` adds [metadata](/docs/expressions#meta), like a `description` or [error parts](#error-messages), to a Type. It applies wherever that Type is referenced, but not to the Types inside it:

```ts
const Password = type("string >= 8").configure({
	message: "Use 8 or more characters"
})

const User = type({
	email: "string.email",
	password: Password
})

// ArkErrors: password: Use 8 or more characters
User({ email: "david@arktype.io", password: "ez123" })
```

## Options

| option                                                      | default                                            | levels               |
| ----------------------------------------------------------- | -------------------------------------------------- | -------------------- |
| [`onUndeclaredKey`](#onundeclaredkey)                       | `"ignore"`                                         | global, type (`"+"`) |
| [`exactOptionalPropertyTypes`](#exactoptionalpropertytypes) | `true`                                             | global, scope        |
| [`numberAllowsNaN`](#numberallowsnan)                       | `false`                                            | global               |
| [`numberAllowsInfinity`](#numberallowsinfinity)             | `false`                                            | global               |
| [`dateAllowsInvalid`](#dateallowsinvalid)                   | `false`                                            | global               |
| [`jitless`](#jitless)                                       | `false`, or `true` where `new Function` is blocked | global, scope        |
| [`onFail`](#onfail)                                         | `null`, which returns `ArkErrors`                  | global, scope        |
| [`errors`](#errors)                                         | `"all"`                                            | global, scope        |
| [`mutatesInput`](#mutatesinput)                             | `false`                                            | global, scope        |
| [`keywords`](#keywords)                                     | `{}`                                               | global               |
| [`locale`](#locale)                                         | `en`                                               | global               |
| [an error code](#by-code), like `divisor`                   | ArkType's messages                                 | global, scope        |
| [`toJsonSchema`](#tojsonschema)                             | draft 2020-12, throwing for what it can't express  | global, scope        |

A Type's own options are its [metadata](/docs/expressions#meta), including the [parts of its errors](#error-messages).

## Error messages

There are two ways to change what an error says:

- **Templated**: configure what the value was expected to be, with a [`description`](#description) or [`expected`](#expected), and what it was, with [`actual`](#actual). ArkType writes "must be `expected`", lists it where a union's error lists its branches' and writes the path before it in a summary.
- **Custom**: configure a [`message`](#message), one whole sentence shown as written wherever the error is read.

```ts
const User = type({
	name: "string",
	age: type("number >= 18").configure({ expected: "an adult's age" }),
	email: type("string.email").configure({ message: "Enter a valid email" })
})

// ArkErrors: name must be a string
//            age must be an adult's age
//            email: Enter a valid email
User({ name: 5, age: 3, email: "x" })
```

`expected`, `actual` and `message` each take a string or a function. See [Errors](/docs/errors) for what an error contains.

### description

What follows "must be" in a message. Other parts and the Type's `.description` reuse it, so it should be your first choice:

```ts
const Even = type("number % 2").describe("an even number")

// ArkErrors: must be an even number
Even(3)
```

### expected

Like `description`, but only for error messages, where it takes precedence. A function receives the error, so it can read `code`, `data` and `path`:

```ts
const Password = type("string >= 8").configure({
	expected: ctx =>
		ctx.code === "minLength" ? `${ctx.rule} characters or more` : "a password"
})

// ArkErrors: must be 8 characters or more
Password("ez123")

// ArkErrors: must be a password
Password(12345678)
```

### actual

What a message ends with, as "(was …)". By default only a missing key's does, with "(was missing)": a message leaves out what the value was, though every error's `actual` still describes its data, like "5" or "an object", for a `message` function to read. Configure a string, or a function of the data, then the error, to write one:

```ts
const Age = type("number <= 100").configure({ actual: data => `${data}` })

// ArkErrors: must be at most 100 (was 101)
Age(101)
```

### message

One whole sentence in place of "must be `expected`". It's the error's `message`, so it's what a [Standard Schema](/docs/standard-schema) consumer, like a form library, shows beside a field, and a summary writes it after the error's path and a colon:

```ts
const Signup = type({
	email: type("string.email").configure({ message: "Enter a valid email" })
})

const out = Signup({ email: "x" })

if (out instanceof type.errors) {
	// email: Enter a valid email
	out.summary

	// Enter a valid email
	out.issues[0].message
}

// a missing key says what its value's message does
// ArkErrors: email: Enter a valid email
Signup({})
```

A message is never composed into another error's, and it applies to the Type it's configured on:

- A union's error lists what its branches expected, not their messages, unless every failing branch has the same message, which the union's error then says.
- A message on a union replaces what it lists. To say what a union must be instead, [describe](#description) it: `type({ a: "string" }).or({ b: "number" }).describe("a shape")` says `must be a shape`.
- A message on a [pipe](/docs/expressions#pipe) is also the message of the errors validating its output.
- A missing key says the message of its whole value, so configure that last, after any `.pipe()` or `.to()`.
- A message doesn't apply to the Types inside its own, so one on an object is what data that isn't an object says, and each key keeps its own.
- A message is what every check of its Type says. For one check's alone, pass that check's [error code](/docs/errors#error-codes) as a [selector](/docs/expressions#meta):

```ts
const Password = type("string >= 8 & /[0-9]/")
	.configure({ message: "Use 8 or more characters" }, "minLength")
	.configure({ message: "Include a number" }, "pattern")

// ArkErrors: Include a number
//            Use 8 or more characters
Password("short")

// ArkErrors: must be a string
Password(5)
```

`"domain"` selects a value of the wrong type, and `"self"` the Type's own node, whose message a missing key says:

```ts
const Sku = type(/^[A-Z]{3}-\d{4}$/)
	.configure({ message: "SKU is required" }, "self")
	.configure({ message: "SKU must be text" }, "domain")

const Product = type({ sku: Sku })

// ArkErrors: sku: SKU is required
Product({})

// ArkErrors: sku: SKU must be text
Product({ sku: 5 })

// ArkErrors: sku must be matched by ^[A-Z]{3}-\d{4}$
Product({ sku: "x" })
```

A code selects every check of that kind in the Type, a nested key's included, so configure a key's value rather than the object around it. A message configured without a selector replaces those configured before it, so configure it first.

A function receives the error, including its `expected` and `actual`. A summary writes its text after the path and a colon as it does a string's, but a missing key doesn't say it:

```ts
const Email = type("string.email").configure({
	message: ctx => `Enter ${ctx.expected}`
})

// ArkErrors: Enter an email address
Email("x")

// ArkErrors: Enter a string
Email(5)
```

Each function also receives the active [locale](/docs/i18n#your-own-messages) as its last argument, so it can write its text in the language a message is read in. A [locale](/docs/i18n#writing-a-locale) also decides how a summary places a path before a message.

### By code

Globally or in a scope, configure errors by their [code](/docs/errors#error-codes). A function's `ctx` is typed by its code:

```ts
const mod = type.module(
	{ isEven: "number % 2" },
	{
		divisor: {
			expected: ctx => `% ${ctx.rule} !== 0`,
			message: ctx => `${ctx.actual} ${ctx.expected}`
		}
	}
)

// ArkErrors: 3 % 2 !== 0
mod.isEven(3)
```

A key that `"+": "reject"` disallows has the code `undeclared`:

```ts
const $ = scope(
	{ User: { "+": "reject", name: "string" } },
	{ undeclared: { message: "This key isn't allowed" } }
)

// ArkErrors: age: This key isn't allowed
$.export().User({ name: "Alice", age: 42 })
```

Each kind of constraint, like `domain` or `divisor`, also takes a `description` function. It receives the constraint and changes how it is described everywhere, not only in errors.

## locale

Error messages are written in English by default. Configure a locale to write them in another language:

```ts title="config.ts"
import { configure } from "arktype/config"
import { de } from "arktype/locales/de"

configure({ locale: de })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

// ArkErrors: muss eine Zeichenkette sein
type.string(5)
```

`locale` can also be a function that returns a locale each time a message is read. See [i18n](/docs/i18n).

## keywords

Configure built-in keywords like `string.email` by name. Each takes a description or the same options as [`.configure`](#type):

```ts title="config.ts"
import { configure } from "arktype/config"

configure({
	keywords: {
		string: "text",
		"string.email": {
			actual: () => "definitely fake"
		}
	}
})
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

const User = type({
	name: "string",
	email: "string.email"
})

// ArkErrors: name must be text
//            email must be an email address (was definitely fake)
User({ name: 5, email: "449 Canal St" })
```

## onUndeclaredKey

Like TypeScript, ArkType ignores keys an object doesn't declare by default. There are three behaviors:

- `"ignore"` (default): allow undeclared keys and keep them in the output
- `"delete"`: allow undeclared keys and output only declared ones
- `"reject"`: fail on undeclared string keys

An undeclared symbol key passes `"reject"` and isn't in `"delete"`'s output.

Set it for one object with [`"+"`](/docs/objects#properties-undeclared), or change the default globally:

```ts title="config.ts"
import { configure } from "arktype/config"

configure({ onUndeclaredKey: "delete" })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

const UserForm = type({
	name: "string"
})

// { name: "Alice" }
UserForm({ name: "Alice", age: "42" })
```

## exactOptionalPropertyTypes

By default, ArkType treats optional keys as TypeScript does with [`exactOptionalPropertyTypes`](https://www.typescriptlang.org/tsconfig/#exactOptionalPropertyTypes): an optional key can be omitted, but not set to `undefined`.

```ts
const MyObj = type({
	"key?": "number"
})

// {}
MyObj({})

// ArkErrors: key must be a number
MyObj({ key: undefined })
```

Add `| undefined` to keys that should accept it. If your tsconfig doesn't enable `exactOptionalPropertyTypes`, you can set ArkType's to `false` to match, which is also how Zod and [most other validators](/docs/migrating#defaults-that-differ) treat optional keys and defaults:

```ts title="config.ts"
import { configure } from "arktype/config"

configure({ exactOptionalPropertyTypes: false })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

const MyObj = type({
	"key?": "number",
	withDefault: "number = 5"
})

// { key: undefined, withDefault: 5 }
MyObj({ key: undefined, withDefault: undefined })
```

With `false`, an explicit `undefined` at a key with a default is replaced by the default, as a missing key is. Treating `null` as missing is tracked in [#1283](https://github.com/arktypeio/arktype/issues/1283).

## numberAllowsNaN

`number` rejects `NaN` by default. Allow it everywhere with `numberAllowsNaN: true`, or in one Type with the `number.NaN` keyword:

```ts
const MaybeNaN = type("number | number.NaN")

// NaN
MaybeNaN(Number.NaN)
```

## numberAllowsInfinity

`number` rejects `Infinity` and `-Infinity` by default. Allow them everywhere with `numberAllowsInfinity: true`, or in one Type with the `number.Infinity` and `number.NegativeInfinity` keywords:

```ts
const Limit = type("number | number.Infinity")

// ArkErrors: must be a number
type.number(Infinity)

// Infinity
Limit(Infinity)
```

## dateAllowsInvalid

`Date` rejects an invalid date, like `new Date("x")`, by default. Allow it with `dateAllowsInvalid: true`:

```ts title="config.ts"
import { configure } from "arktype/config"

configure({ dateAllowsInvalid: true })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

// Invalid Date
type("Date")(new Date("x"))
```

## jitless

ArkType compiles each Type to optimized validation code using `new Function`. Where that's blocked, it validates without compiling instead, which is up to about 30x slower per call on a plain object, and 3x to 5x on invalid data or a morph.

Cloudflare Workers allow `new Function` only as a Worker loads, and a Type compiles once it's used, so a Type first used within a request isn't compiled. To check with compiled code there, [precompile](/docs/precompile) your Types, or read a Type's `precompilation` where it's defined, which compiles it as the Worker loads and adds to its startup.

To turn compiling off yourself, set `jitless: true`:

```ts title="config.ts"
import { configure } from "arktype/config"

configure({ jitless: true })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

// will not be compiled
const MyObject = type({
	foo: "string"
})
```

Configuring `jitless` globally also skips the check for `new Function`, which a strict Content-Security-Policy would report as a violation. To validate without generating code and without shipping the parser, [precompile](/docs/precompile) your Types when you build.

## errors

By default, a failed validation returns an error for each check that failed. `errors` can return less:

- `"all"` (default): every error, at each path that failed
- `"first"`: the first error validation finds, where it stops
- `"none"`: one error at the root, whose message is `is invalid`

```ts title="config.ts"
import { configure } from "arktype/config"
import "arktype/errors"

configure({ errors: "none" })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

const User = type({ name: "string", age: "number" })

// ArkErrors: is invalid
const out = User({ name: 5, age: "5" })
```

`"first"` and `"none"` are installed by `import "arktype/errors"`, so a program choosing neither ships neither. Without it, creating a Type configured with either throws.

With `"first"`, which of the data's errors is returned isn't promised, and can differ between a Type and its precompiled validator.

With `"none"`, a failure returns one error with the code `"predicate"`, an empty path and the data. It's still an instance of `type.errors`, `.assert()` throws a `TraversalError` saying `is invalid`, and its message isn't [localized](#locale). A narrow or morph that reads `ctx.errors` while validating sees each issue added so far written the same way, as `is invalid` at its own path.

`errors` can also be set per Scope. It applies to that Scope's Types, including where another Scope references them.

A [precompiled](/docs/precompile/options#errors) build takes `errors` as an option.

## mutatesInput

By default, a transform copies each object it changes other than a builtin like a `Date`, so the data you pass is otherwise never written. `mutatesInput` writes what a Type transforms, its defaults and its morphed values, into the data, which it returns:

- `false` (default): copies each object it changes
- `true`: writes in place where no other part of the Type can read the write, and otherwise copies
- `"always"`: writes every transform in place

```ts title="config.ts"
import { configure } from "arktype/config"
import "arktype/mutatesInput"

configure({ mutatesInput: true })
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

const User = type({ name: "string.trim", role: "string = 'member'" })

const data = { name: " Ada " }

// true, and data is now { name: "Ada", role: "member" }
const isData = Object.is(User(data), data)
```

`true` and `"always"` are installed by `import "arktype/mutatesInput"`, so a program choosing neither ships neither. Without it, creating a Type configured with either throws.

`true` always returns what copying would. `"always"` requires that the data hold no object at two places a transform reaches, and that a Type's functions read or return the data's objects only through the value each is passed, not `ctx.root`.

The object returned is the data, so it keeps its key order, accessors and inherited keys. Where the data holds one object at two places, a key the Type doesn't declare can hold what the other place wrote. An object a Type deletes undeclared keys from is still copied. A failed validation can leave writes in the objects of its data it found valid.

`mutatesInput` can also be set for a Scope, whose Types then transform as it says.

A [precompiled](/docs/precompile/options#mutatesinput) build takes `mutatesInput` as an option.

## onFail

To throw on every failed validation, or transform its result some other way, configure `onFail`. Declare its return type on `ArkEnv` so calls are typed to match:

```ts title="config.ts"
import { configure } from "arktype/config"

const config = configure({
	onFail: errors => errors.throw()
})

declare global {
	interface ArkEnv {
		onFail: typeof config.onFail
	}
}
```

```ts title="app.ts"
import "./config.ts"
import { type } from "arktype"

// string, since a failure throws instead of returning ArkErrors
const data = type.string("foo")

// TraversalError: must be a string
type.string(5)
```

`onFail` can also be passed to a scope.

## toJsonSchema

`toJsonSchema` sets the defaults for `.toJsonSchema()`, like its target and how to handle what JSON Schema can't express. See [JSON Schema](/docs/json-schema/to-json-schema).

## metadata

<AnchorAliases custom />

Add your own keys to the metadata Types accept by extending `ArkEnv`:

```ts
// add this anywhere in your project
declare global {
	interface ArkEnv {
		meta(): {
			// meta properties should always be optional
			secretIngredient?: string
		}
	}
}

// now types you define can specify and access your metadata
const MrPingsSecretIngredientSoup = type({
	broth: "'miso' | 'vegetable'",
	ingredients: "string[]"
}).configure({ secretIngredient: "nothing!" })
```

## prototypes

When you `.infer` a Type, ArkType walks its inferred type to extract special values like morphs, e.g. `(In: string) => Out<number>`. For some classes that walk is slow or expands the type. Declare them in `prototypes` to have them treated as opaque:

```ts
declare global {
	interface ArkEnv {
		prototypes(): MySpecialClass
	}
}

class MySpecialClass {}

// Type<MySpecialClass>
const T = type.instanceOf(MySpecialClass)
```
