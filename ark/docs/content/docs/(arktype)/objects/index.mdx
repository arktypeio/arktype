## properties

An object definition can combine required, optional and defaultable keys with index signatures.

### required [#properties-required]

<SyntaxTabs>
	<SyntaxTab string>

```ts
const symbolicKey = Symbol()

const MyObj = type({
	requiredKey: "string",
	// nested definitions don't need their own type call
	[symbolicKey]: {
		nested: "unknown"
	}
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const symbolicKey = Symbol()

const MyObj = type({
	requiredKey: type.string,
	// nested definitions don't need their own type call
	[symbolicKey]: {
		nested: type.unknown
	}
})
```

    </SyntaxTab>

</SyntaxTabs>

### optional [#properties-optional]

<SyntaxTabs>
	<SyntaxTab string>

```ts
const symbolicKey = Symbol()

const MyObj = type({
	"optionalKey?": "number[]",
	[symbolicKey]: "string?"
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const symbolicKey = Symbol()

const MyObj = type({
	optionalKey: type.number.array().optional(),
	[symbolicKey]: type.string.optional()
})
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const symbolicKey = Symbol()

const MyObj = type({
	optionalKey: ["number[]", "?"],
	[symbolicKey]: ["string", "?"]
})
```

    </SyntaxTab>

</SyntaxTabs>

<Callout type="info" title="Key or value syntax?">

Prefer the key syntax, `"key?"`. It mirrors TypeScript and reads as what it is: a constraint on whether the key is present, not on its value.

Put `?` on the value when the key is a symbol, when you want go-to-definition and JSDoc on an unquoted key, or when you'd rather not quote keys.

</Callout>

<Callout type="warn" title="An optional key doesn't allow undefined">

ArkType checks optional keys the way TypeScript does with [`exactOptionalPropertyTypes`](https://www.typescriptlang.org/tsconfig#exactOptionalPropertyTypes): a missing key is valid, but a key set to `undefined` must allow `undefined`.

```ts
const MyObj = type({
	"key?": "number"
})

// {}
MyObj({})

// ArkErrors: key must be a number (was undefined)
MyObj({ key: undefined })
```

To allow it, add `undefined` to the value: `"key?": "number | undefined"`. You can also set [`exactOptionalPropertyTypes`](/docs/configuration#exactoptionalpropertytypes) to `false` globally.

</Callout>

### defaultable [#properties-defaultable]

A defaultable key is optional in the input. When it is missing, the output has its default.

<SyntaxTabs>
	<SyntaxTab string>

```ts
const MyObj = type({
	defaultableKey: "boolean = false"
})

// { defaultableKey: false }
MyObj({})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const MyObj = type({
	defaultableKey: type.boolean.default(false)
})

// { defaultableKey: false }
MyObj({})
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const MyObj = type({
	defaultableKey: ["boolean", "=", false]
})

// { defaultableKey: false }
MyObj({})
```

    </SyntaxTab>

</SyntaxTabs>

`= []` and `= {}` give each output its own new array or object, so mutating one never changes another:

```ts
const MyObj = type({
	values: "string[] = []",
	meta: "object = {}"
})
```

For any other object, default to a function that returns it, e.g. `type.Date.default(() => new Date())`.

<Callout type="warn" title="Optional and default only work in objects and tuples">

`number.optional()` and `number.default(0)` don't return a `Type`. They return the tuple definitions `[Type<number>, "?"]` and `[Type<number>, "=", 0]`, which are only valid as a property or a tuple element. `type("string?")` throws a `ParseError`.

For a `Type` that accepts `undefined`, use a union like `type("string | undefined")`. To replace `undefined` with a value, add a morph:

```ts
const FallbackString = type("string | undefined").pipe(v => v ?? "")
```

</Callout>

### index [#properties-index]

An index signature constrains every key that matches it:

```ts
const Scores = type({
	"[string]": "number"
})
```

The key can be any string or symbol type, like `symbol`, `string | symbol`, a keyword like `string.uuid` or a regex literal:

```ts
const DataAttributes = type({
	"[/^data-/]": "string"
})

// ArkErrors: value at ["data-id"] must be a string (was a number)
DataAttributes({ "data-id": 1 })
```

A union of literal keys becomes those named keys, so `"['a' | 'b']": "number"` is `{ a: number, b: number }`.

`Record` is available as a [generic keyword](/docs/generics#keywords), e.g. `type("Record<string, number>")` or `type.Record("string", "number")`.

### undeclared [#properties-undeclared]

By default, ArkType allows keys you didn't declare, like TypeScript does. That lets you validate an object you already have without copying it, and skipping the check for extra keys is faster.

To reject or delete undeclared keys, set `"+"` in the object, or [configure](/docs/configuration#onundeclaredkey) a different default for every object:

<SyntaxTabs>
	<SyntaxTab string>

```ts
// fail if any string key other than "onlyAllowedKey" is present
const MyClosedObject = type({
	"+": "reject",
	onlyAllowedKey: "string"
})

// delete every key other than "onlyPreservedKey"
const MyStrippedObject = type({
	"+": "delete",
	onlyPreservedKey: "string"
})

// allow and keep undeclared keys (the default)
const MyOpenObject = type({
	"+": "ignore",
	nonexclusiveKey: "number"
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// fail if any string key other than "onlyAllowedKey" is present
const MyClosedObject = type({
	onlyAllowedKey: "string"
}).onUndeclaredKey("reject")

// delete every key other than "onlyPreservedKey"
const MyStrippedObject = type({
	onlyPreservedKey: "string"
}).onUndeclaredKey("delete")

// allow and keep undeclared keys (the default)
const MyOpenObject = type({
	nonexclusiveKey: "number"
}).onUndeclaredKey("ignore")
```

    </SyntaxTab>

</SyntaxTabs>

`"ignore"` only matters if you configured a different default.

A rejected key is an error with the code `undeclared`:

```ts
const MyClosedObject = type({
	"+": "reject",
	onlyAllowedKey: "string"
})

// ArkErrors: extraKey must be removed
MyClosedObject({ onlyAllowedKey: "ok", extraKey: 1 })
```

Both act on string keys: `"reject"` checks only an object's string keys, and `"delete"` builds a new object holding only its declared keys. So an undeclared symbol key passes `"reject"` and is dropped by `"delete"`, and reject types that differ only by a symbol key overlap, so a union of them with a morph is indeterminate.

`"delete"`'s output lists the declared keys in the order the definition declares them, as Zod does, then any keys matching an index signature in the input's order.

`.onDeepUndeclaredKey()` applies the same behavior to every nested object:

```ts
const MyDeeplyStrippedObject = type({
	preserved: "string",
	nested: {
		preserved: "string"
	}
}).onDeepUndeclaredKey("delete")

// { nested: { preserved: "b" }, preserved: "a" }
MyDeeplyStrippedObject({
	preserved: "a",
	extra: 1,
	nested: { preserved: "b", extra: 2 }
})
```

<Callout type="info" title="Prefer in-object syntax where possible">

`.onUndeclaredKey()` and `.configure()` rebuild the whole type they're called on, so creating a type with them is slower than writing `"+"` in the object. Validation is equally fast either way. Methods like `.or()` and `.pipe()` reference the original type rather than rebuilding it, so they have no such cost.

</Callout>

<AnchorAliases properties-merge spread properties-spread />
### merge

Merging adds properties to an object or replaces existing ones, like JavaScript's [spread syntax](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/Spread_syntax). Write it as a `"..."` key in the object, `.merge()` or the `Merge` generic:

<SyntaxTabs>
	<SyntaxTab string>

```ts
const User = type({ isAdmin: "false", name: "string" })

// Type<{ name: string; isAdmin: true; permissions: string[] }>
const Admin = type({
	"...": User,
	isAdmin: "true",
	permissions: "string[]"
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const User = type({ isAdmin: "false", name: "string" })

// Type<{ name: string; isAdmin: true; permissions: string[] }>
const Admin = User.merge({
	isAdmin: "true",
	permissions: "string[]"
})
```

    </SyntaxTab>

    <SyntaxTab generic>

```ts
const types = type.module({
	User: { isAdmin: "false", name: "string" },
	AdminProps: { isAdmin: "true", permissions: "string[]" },
	// { name: string; isAdmin: true; permissions: string[] }
	Admin: "Merge<User, AdminProps>"
})
```

    </SyntaxTab>

</SyntaxTabs>

A key in both objects takes its value from the merged object. An [intersection](/docs/expressions#intersection) would instead intersect the two values, and `false & true` would throw a `ParseError`. When the keys don't overlap, the two give the same type, but merging is less work to compute, both when the type is created and in your editor, so prefer it for combining properties.

Like the other [structural transformations](/docs/objects#properties-structural), `merge` builds a new object from the properties, so a root narrow or metadata is not carried over.

<AnchorAliases merge-n-ary />
#### n-ary

`type.merge` merges any number of objects, each overriding the ones before it:

```ts
// Type<{ b: number; a?: 1 }>
const Merged = type.merge({ a: "string" }, { b: "number" }, { "a?": "1" })
```

### escapes [#properties-escapes]

Escape a key's `?`, the `[` of a key in brackets, or a key that is exactly `+`, `...` or `@`, with a backslash to use it literally:

```ts
// Type<{ "isAdmin?": boolean; "+": string; "[id]"?: string }>
const Escaped = type({
	"isAdmin\\?": "boolean",
	"\\+": "string",
	"\\[id]?": "string"
})

// ArkErrors: value at ["isAdmin?"] must be boolean (was missing)
Escaped({ "+": "x" })
```

An index signature can't be optional, so a key like `"[id]?"` throws a `ParseError` unless its `[` is escaped.

### keyof [#properties-keyof]

Like in TypeScript, `keyof` extracts an object's keys as a union:

<SyntaxTabs>
	<SyntaxTab string>

```ts
const types = type.module({
	UsedCar: {
		originallyPurchased: "string.date",
		remainingWheels: "number"
	},
	// "originallyPurchased" | "remainingWheels"
	UsedCarKey: "keyof UsedCar"
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const UsedCar = type({
	originallyPurchased: "string.date",
	remainingWheels: "number"
})

// Type<"originallyPurchased" | "remainingWheels">
const UsedCarKey = UsedCar.keyof()
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const UsedCar = type({
	originallyPurchased: "string.date",
	remainingWheels: "number"
})

// Type<"originallyPurchased" | "remainingWheels">
const UsedCarKey = type(["keyof", UsedCar])
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
const UsedCar = type({
	originallyPurchased: "string.date",
	remainingWheels: "number"
})

// Type<"originallyPurchased" | "remainingWheels">
const UsedCarKey = type("keyof", UsedCar)
```

    </SyntaxTab>

</SyntaxTabs>

Also like in TypeScript, a `[string]` index signature absorbs the named keys, so `keyof` is `string`:

```ts
const RecordWithSpecialKeys = type({
	"[string]": "unknown",
	verySpecialKey: "number"
})

// true
RecordWithSpecialKeys.keyof().equals("string")
```

<Callout type="warn" title="ArkType's keyof never includes number">

TypeScript's `keyof` can include `number`, but JavaScript has no numeric keys: `{ 4: true }` and `{ "4": true }` are the same object, and `Object.keys` returns `["4"]` for both. ArkType's `keyof` only returns `string` and `symbol` keys, the two kinds of key an object can have.

<details>
	<summary>Why ArkType diverges from TypeScript here</summary>

In a set-based type system, two types that describe the same values need the same representation. TypeScript keeps separate numeric and string representations of the same key, which leads to results like this:

```ts
type Thing1 = {
	[x: string]: unknown
}

// Thing2 describes the same values as Thing1
type Thing2 = Record<string, unknown>

type Key1 = keyof Thing1
//   ^?

type Key2 = keyof Thing2
//   ^?
```

</details>

</Callout>

### get [#properties-get]

Like an indexed access type in TypeScript (`User["name"]`), `get` extracts the type of the value at a key:

```ts
const Manatee = type({
	isFriendly: "true",
	snorf: {
		uses: "string[]"
	}
})

// Type<true>
const IsFriendly = Manatee.get("isFriendly")

// pass more keys to access nested properties
// Type<string[]>
const SnorfUses = Manatee.get("snorf", "uses")
```

The key can also be a union, a literal or an index signature, and the object can be a union with optional keys. The [`get` tests](https://github.com/arktypeio/arktype/blob/main/ark/type/__tests__/get.test.ts) cover each case.

<Callout type="warn" title="Extracting part of a type can be an antipattern">

Before using `get`, `pick` or `omit` on a type you defined, consider defining that part as its own type and referencing it. Composing small types is usually clearer and faster than extracting parts of a large one.

</Callout>

### structural transformations [#properties-structural]

`merge`, `pick`, `omit`, `required`, `partial` and `map` each return a **new object built from the properties** of the `Type` they're called on, rather than referencing that `Type`.

<Callout type="warn" title="Only properties are carried over">

Anything attached to the object itself is dropped: most importantly a root [narrow](/docs/expressions#narrow) or [filter](/docs/expressions#filter), but also [metadata](/docs/configuration#metadata) like `.describe(...)`. Constraints on the properties are kept.

```ts
const User = type({
	name: "string",
	email: "string"
}).narrow(user => user.email.includes("@"))

// the narrow is not a property, so PartialUser doesn't have it
const PartialUser = User.partial()

// { email: "not an email" }
PartialUser({ email: "not an email" })
```

Reapply what you still need to the result:

```ts
const PartialUser = type({
	name: "string",
	email: "string"
})
	.partial()
	.narrow(user => user.email?.includes("@") ?? true)
```

A root [morph](/docs/expressions#pipe) can't be reduced to properties, so transforming a type like `type({ name: "string" }).pipe(user => user)` throws a `ParseError` instead of dropping it.

</Callout>

### pick / omit [#properties-pick-omit]

Keep or remove specific properties:

```ts
const User = type({
	name: "string",
	email: "string.email",
	"age?": "number"
})

// Type<{ name: string; email: string }>
const NameAndEmail = User.pick("name", "email")

// Type<{ name: string; age?: number }>
const WithoutEmail = User.omit("email")
```

In a definition, use the `Pick` and `Omit` [generics](/docs/generics#keywords). Their keys are definitions, so quote each one:

```ts
const types = type.module({
	User: {
		name: "string",
		email: "string.email",
		"age?": "number"
	},
	NameAndEmail: "Pick<User, 'name' | 'email'>",
	WithoutEmail: "Omit<User, 'email'>"
})
```

### required / partial [#properties-required-partial]

Make every named property required or optional:

```ts
const User = type({
	name: "string",
	"email?": "string.email",
	"age?": "number"
})

// Type<{ name: string; email: string; age: number }>
const RequiredUser = User.required()

// Type<{ name?: string; email?: string; age?: number }>
const PartialUser = User.partial()
```

`required` also removes defaults, so a defaulted key becomes a plain required key:

```ts
// Type<{ foo: string }>
const T = type({ foo: "string = 'bar'" }).required()

// ArkErrors: foo must be a string (was missing)
T({})
```

In a definition, use the `Required` and `Partial` [generics](/docs/generics#keywords), e.g. `"Partial<User>"` in a scope.

<Callout type="info" title="Arrays and tuples mirror TypeScript's Required and Partial">

Like the mapped types they're named for, `required` and `partial` apply to an array's or tuple's elements:

```ts
// Type<[string?, number?]>
const PartialPair = type(["string", "number"]).partial()

// Type<[string, number]>
const RequiredPair = type(["string", "number?"]).required()
```

They only change whether an element must be present, never the values it allows. TypeScript also adds `undefined` to variadic elements and index signature values, since it has no way to mark them optional. ArkType doesn't, so `type("string[]").partial()` is still `string[]`.

A postfix element can't follow an optional one, in ArkType or in TypeScript, so `partial` throws a `ParseError` on a tuple like `[string, ...number[], boolean]`.

</Callout>

### readonly [#properties-readonly]

Mark every property as `readonly`. This only affects the inferred type; the output isn't frozen.

```ts
// Type<{ readonly id: number; readonly name: string }>
const Frozen = type({
	id: "number",
	name: "string"
}).readonly()
```

### map [#properties-map]

`map` transforms each property of an object. The function receives a prop with its `key`, `value` (a `Type`) and `kind` (`"required"` or `"optional"`), and returns a `{ key, value }` object, optionally with `kind`:

```ts
const Name = type({
	first: "string",
	last: "string"
})

// Type<{ first: string | null; last: string | null }>
const NullableName = Name.map(prop => ({
	key: prop.key,
	value: prop.value.or("null")
}))
```

Return `[]` to remove a property, or several props to add more than one:

```ts
const User = type({
	name: "string",
	"age?": "number"
})

// Type<{ name: string }>
const NameOnly = User.map(prop => (prop.key === "age" ? [] : prop))
```

### props [#properties-props]

`props` lists an object's properties, with required keys first, then optional keys, each sorted by name:

```ts
const User = type({
	name: "string",
	"age?": "number",
	role: "'admin' | 'user' = 'user'"
})

for (const prop of User.props) {
	console.log(prop.kind) // "required", "optional", "optional"
	console.log(prop.key) // "name", "age", "role"
	console.log(prop.value.expression) // "string", "number", '"admin" | "user"'
	if ("default" in prop) console.log(prop.default) // "user"
}
```

## tuples

Like objects, tuples are structures whose values are nested definitions. Like TypeScript, ArkType supports prefix, defaultable, optional, variadic and postfix elements, with the same rules for combining them.

### prefix [#tuples-prefix]

<SyntaxTabs>
	<SyntaxTab string>

```ts
const MyTuple = type([
	"string",
	// object definitions can be nested in tuples, and vice versa
	{
		coordinates: ["number", "number"]
	}
])
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const MyTuple = type([
	type.string,
	// object definitions can be nested in tuples, and vice versa
	{
		coordinates: [type.number, type.number]
	}
])
```

    </SyntaxTab>

</SyntaxTabs>

### defaultable [#tuples-defaultable]

A defaultable element is optional in the input. When it is missing, the output has its default.

Defaultable elements follow the prefix elements and come before any optional elements. Like optional elements, they can't be combined with postfix elements.

<SyntaxTabs>
	<SyntaxTab string>

```ts
const MyTuple = type(["string", "boolean = false", "number = 0"])

// ["a", false, 0]
MyTuple(["a"])
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const MyTuple = type([
	type.string,
	type.boolean.default(false),
	type.number.default(0)
])

// ["a", false, 0]
MyTuple(["a"])
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const MyTuple = type(["string", ["boolean", "=", false], ["number", "=", 0]])

// ["a", false, 0]
MyTuple(["a"])
```

    </SyntaxTab>

</SyntaxTabs>

### optional [#tuples-optional]

An optional element may be absent from the input and has no default.

Optional elements follow the prefix and defaultable elements, and come before a variadic element or the end of the tuple. Like in TypeScript, they can't be combined with postfix elements.

<SyntaxTabs>
	<SyntaxTab string>

```ts
const MyTuple = type(["string", "boolean?", "number?"])

// ["a"]
MyTuple(["a"])
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const MyTuple = type([
	type.string,
	type.boolean.optional(),
	type.number.optional()
])

// ["a"]
MyTuple(["a"])
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const MyTuple = type(["string", ["boolean", "?"], ["number", "?"]])

// ["a"]
MyTuple(["a"])
```

    </SyntaxTab>

</SyntaxTabs>

### variadic [#tuples-variadic]

Like in TypeScript, a variadic element allows zero or more consecutive values of a type. A tuple can have at most one. Write it as `"..."` followed by an array:

<SyntaxTabs>
	<SyntaxTab string>

```ts
// a string followed by zero or more numbers
const MyTuple = type(["string", "...", "number[]"])
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// a string followed by zero or more numbers
const MyTuple = type([type.string, "...", type.number.array()])
```

    </SyntaxTab>

</SyntaxTabs>

### postfix [#tuples-postfix]

Postfix elements are required elements after a variadic element. They can't be combined with optional or defaultable elements.

<SyntaxTabs>
	<SyntaxTab string>

```ts
// zero or more numbers followed by a boolean, then a string
const MyTuple = type(["...", "number[]", "boolean", "string"])
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// zero or more numbers followed by a boolean, then a string
const MyTuple = type(["...", type.number.array(), type.boolean, type.string])
```

    </SyntaxTab>

</SyntaxTabs>

## dates

`Date` allows a valid `Date` instance. An invalid date, like `new Date("x")`, is rejected:

```ts
// ArkErrors: must be a Date (was an invalid Date)
type.Date(new Date("x"))
```

To accept invalid dates everywhere, configure [`dateAllowsInvalid`](/docs/configuration#dateallowsinvalid).

### literals [#dates-literals]

A date literal, `d'...'` or `d"..."`, is a `Date` with an exact value. They're mostly useful as [range](/docs/objects#dates-ranges) bounds.

```ts
const Literals = type({
	singleQuoted: "d'1970-01-01'",
	doubleQuoted: 'd"1970-01-01"'
})
```

A literal, like a string passed as a date limit, must be the same instant on every machine, so it can be an ISO date like `2025-01-01` (which is UTC), an ISO date-time with `Z` or an offset like `2025-01-01T12:00+01:00`, or a number of epoch milliseconds. Any other literal, like `d'notadate'` or `d'2025-01-01T12:00'`, is a `ParseError`.

### ranges [#dates-ranges]

Constrain a `Date` with `>`, `>=`, `<`, `<=`, `==` or `!=`. A bound is either a [date literal](/docs/objects#dates-literals) or a number of milliseconds since the Unix epoch.

<SyntaxTabs>
	<SyntaxTab string>

```ts
const Bounded = type({
	inThePast: `Date < ${Date.now()}`,
	from2000: "Date >= d'2000-01-01'",
	before2100: "Date < d'2100-01-01'"
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const Bounded = type({
	inThePast: type.Date.earlierThan(Date.now()),
	from2000: type.Date.atOrAfter("2000-01-01"),
	before2100: type.Date.earlierThan("2100-01-01")
})
```

    </SyntaxTab>

</SyntaxTabs>

The fluent methods are `laterThan`, `atOrAfter`, `earlierThan` and `atOrBefore`.

A range sets both bounds at once, each inclusive or exclusive:

<SyntaxTabs>
	<SyntaxTab string>

```ts
const tenYearsAgo = new Date().setFullYear(new Date().getFullYear() - 10)

const Recent = type(`${tenYearsAgo} <= Date < ${Date.now()}`)
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const tenYearsAgo = new Date().setFullYear(new Date().getFullYear() - 10)

const Recent = type.Date.atOrAfter(tenYearsAgo).earlierThan(Date.now())
```

    </SyntaxTab>

</SyntaxTabs>

Descriptions and error messages write dates in UTC. A date at UTC midnight is written as its calendar date:

```ts
// "a Date and January 1, 2023 or later"
type("Date >= d'2023-01-01'").description

// "a Date and January 1, 2023, 2:30 PM UTC or later"
type("Date >= d'2023-01-01T14:30Z'").description
```

## instanceof

Most built-in classes like `Array`, `Date` and `Map` are [keywords](/docs/keywords#instanceof). Use `instanceof` for your own classes:

<SyntaxTabs>
	<SyntaxTab fluent>

```ts
class MyClass {}

const Instance = type.instanceOf(MyClass)
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
class MyClass {}

const Instance = type(["instanceof", MyClass])
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
class MyClass {}

const Instance = type("instanceof", MyClass)
```

    </SyntaxTab>

</SyntaxTabs>

<Callout type="info" title="Array is the only constructor that works across realms">

Constructors are compared by identity, so a value created in another realm, like an `<iframe>` or a `node:vm` context, is not an instance of the constructor in yours. `Array` is checked with `Array.isArray`, so it also matches arrays from another realm.

</Callout>

### keywords [#instanceof-keywords]

The [keywords](/docs/keywords#instanceof) page lists every built-in class keyword, along with the subtypes of [Array](/docs/keywords#array) and [FormData](/docs/keywords#formdata).

Keywords for web platform classes, like `Blob`, `File`, `URL`, `FormData`, `Headers`, `Request` and `Response`, throw when used in a runtime that doesn't define that class, e.g. `'Blob' is unresolvable`.
