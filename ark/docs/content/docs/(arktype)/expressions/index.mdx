title: Expressions
description: Combine, refine, transform and annotate types with operators like unions, intersections, narrows, pipes, brands and metadata.
---

An expression combines or modifies other definitions. Most expressions can be written four ways:

- **string**: embedded in a string definition, like `"string | number"`
- **fluent**: a method on a `Type`, like `type.string.or(type.number)`
- **tuple**: an array definition, like `["string", "|", "number"]`
- **args**: the same elements passed to `type` as arguments, like `type("string", "|", "number")`

They're interchangeable, so use whichever reads best. Where an operand is a function or a value like a symbol, use the fluent, tuple or args form.

| Expression                                     | String             | Fluent                   | Tuple / args            |
| ---------------------------------------------- | ------------------ | ------------------------ | ----------------------- |
| [intersection](/docs/expressions#intersection) | `"a & b"`          | `.and(b)`                | `[a, "&", b]`           |
| [union](/docs/expressions#union)               | `"a \| b"`         | `.or(b)`                 | `[a, "\|", b]`          |
| [array](/docs/objects#arrays)                  | `"a[]"`            | `.array()`               | `[a, "[]"]`             |
| [keyof](/docs/objects#properties-keyof)        | `"keyof a"`        | `.keyof()`               | `["keyof", a]`          |
| [brand](/docs/expressions#brand)               | `"a#name"`         | `.brand("name")`         |                         |
| [narrow](/docs/expressions#narrow)             |                    | `.narrow(fn)`            | `[a, ":", fn]`          |
| [filter](/docs/expressions#filter)             |                    | `.filter(fn)`            |                         |
| [pipe](/docs/expressions#pipe)                 |                    | `.pipe(fn)`              | `[a, "=>", fn]`         |
| [to](/docs/expressions#to)                     | `"a \|> b"`        | `.to(b)`                 | `[a, "\|>", b]`         |
| [unit](/docs/expressions#unit)                 | a literal, `"'a'"` | `type.unit(value)`       | `["===", value]`        |
| [meta](/docs/expressions#meta)                 |                    | `.configure(meta)`       | `[a, "@", meta]`        |
| [instanceof](/docs/objects#instanceof)         |                    | `type.instanceOf(Class)` | `["instanceof", Class]` |

Optional (`?`), defaultable (`=`) and spread (`...`) definitions only apply to properties and tuple elements. They're covered on the [objects](/docs/objects) page.

## Intersection

Like its TypeScript counterpart, an intersection creates a `Type` that enforces the constraints of both operands.

<SyntaxTabs>
	<SyntaxTab string>

```ts
// an email address at arktype.io
const ArkEmail = type("string.email & /@arktype\\.io$/")

// ArkErrors: must be matched by @arktype\.io$ (was "a@b.com")
ArkEmail("a@b.com")
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// an email address at arktype.io
const ArkEmail = type("string.email").and(/@arktype\.io$/)

// ArkErrors: must be matched by @arktype\.io$ (was "a@b.com")
ArkEmail("a@b.com")
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
// an email address at arktype.io
const ArkEmail = type(["string.email", "&", /@arktype\.io$/])

// ArkErrors: must be matched by @arktype\.io$ (was "a@b.com")
ArkEmail("a@b.com")
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
// an email address at arktype.io
const ArkEmail = type("string.email", "&", /@arktype\.io$/)

// ArkErrors: must be matched by @arktype\.io$ (was "a@b.com")
ArkEmail("a@b.com")
```

    </SyntaxTab>

</SyntaxTabs>

<Callout type="warn" title="To combine properties, merge instead">

Intersecting objects is more work to compute than [merging](/docs/objects#merge) them, both when the type is created and in your editor. Unless you need overlapping keys' values intersected, merge.

</Callout>

<AnchorAliases intersection-n-ary />
### n-ary

`type.and` intersects any number of definitions:

```ts
// Type<{ foo: string; bar: number; baz: string }>
const FooBarBaz = type.and(
	{ foo: "string" },
	{ bar: "number" },
	{ baz: "string" }
)
```

## Union

A union allows a value that satisfies either operand. ArkType discriminates unions automatically: where a value like its type or a literal key tells the branches apart, it checks that first instead of trying each branch, which keeps validation fast and errors specific. Where the discriminant can't place data, like a number where every branch is an object, each branch reports its own error, as in an undiscriminated union.

<SyntaxTabs>
	<SyntaxTab string>

```ts
const StringOrNumber = type("string | number")

// ArkErrors: must be a number or a string (was boolean)
StringOrNumber(true)
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
const StringOrNumber = type.string.or(type.number)

// ArkErrors: must be a number or a string (was boolean)
StringOrNumber(true)
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const StringOrNumber = type(["string", "|", "number"])

// ArkErrors: must be a number or a string (was boolean)
StringOrNumber(true)
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
const StringOrNumber = type("string", "|", "number")

// ArkErrors: must be a number or a string (was boolean)
StringOrNumber(true)
```

    </SyntaxTab>

</SyntaxTabs>

When no branch matches the discriminant, like a value of the wrong type here, the error's code is `discriminant`. See [errors](/docs/errors) for the fields it carries.

<AnchorAliases union-n-ary />
### n-ary

`type.or` unions any number of definitions:

```ts
// Type<string | number | { key: unknown }>
const Union = type.or(type.string, "number", { key: "unknown" })
```

<AnchorAliases union-morphs />

<Callout type="warn" title="A union that could transform the same input in different ways throws a ParseError">

```ts
// operands overlap, but neither transforms data
const Okay = type("number > 0").or("number < 10")

// an operand transforms data, but the inputs don't overlap
const AlsoOkay = type("string.numeric.parse").or({ box: "string" })

// ParseError: An unordered union of a type including a morph and a type with overlapping input is indeterminate
const Bad = type({ box: "string.numeric.parse" }).or({ box: "string" })
```

To fix it, make the inputs disjoint, e.g. by narrowing a morph's input, or pipe the union of their inputs to a single morph:

```ts
// only numeric strings are parsed, so no input reaches two branches
const Narrowed = type("string.numeric.parse | number | null")

// one morph decides how to transform each input
const Piped = type("unknown").pipe(v => (v === null ? v : Number(v)))
```

<details>
	<summary>Why this isn't allowed</summary>

`Bad` says two things about the same input:

- if `box` is a string, parse it as a number
- if `box` is a string, keep it as a string

The order of a union's branches doesn't affect its result, so there's no way to choose between them. The same applies when the transformed keys differ: `type({ a: "string.numeric.parse" }).or({ b: "string.numeric.parse" })` throws too, since an input like `{ a: "1", b: "2" }` matches both branches and each would parse a different key.

</details>

</Callout>

### extract / exclude [#extract-exclude]

`.extract()` keeps the branches of a union that are assignable to a definition, and `.exclude()` removes them, like TypeScript's `Extract` and `Exclude`:

```ts
const Primitive = type("string | number | boolean")

// Type<number | boolean>
const NumberOrBoolean = Primitive.extract("number | boolean")

// Type<number | boolean>
const NotString = Primitive.exclude("string")
```

In a definition, use the `Extract` and `Exclude` [generics](/docs/generics#keywords), e.g. `"Exclude<'a' | 'b' | 0, string>"`.

## Brand

A brand adds a type-only tag to a type, so the only values that satisfy it are those you validated with it.

<SyntaxTabs>
	<SyntaxTab string>

```ts
// @errors: 2322
const Even = type("(number % 2)#even")
type Even = typeof Even.infer

const good: Even = Even.assert(2)
// TypeScript: Type 'number' is not assignable to type 'Brand<number, "even">'
const bad: Even = 5
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// @errors: 2322
const Even = type.number.divisibleBy(2).brand("even")
type Even = typeof Even.infer

const good: Even = Even.assert(2)
// TypeScript: Type 'number' is not assignable to type 'Brand<number, "even">'
const bad: Even = 5
```

    </SyntaxTab>

</SyntaxTabs>

A brand changes nothing at runtime. The `Brand` type it infers is exported from `arktype`.

For more on branding in general, see [this article](https://www.learningtypescript.com/articles/branded-types) by [Josh Goldberg](https://github.com/joshuakgoldberg).

## Narrow

A narrow adds custom validation to a type. Return `true` to accept the value, or call `ctx.mustBe()` or `ctx.reject()` to reject it with a message. The [intro](/docs/intro/adding-constraints#narrow) walks through an example.

<SyntaxTabs>
	<SyntaxTab fluent>

```ts
const Palindrome = type("string").narrow(
	(s, ctx) => s === [...s].reverse().join("") || ctx.mustBe("a palindrome")
)

// ArkErrors: must be a palindrome (was "arktype")
Palindrome("arktype")
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const Palindrome = type([
	"string",
	":",
	(s, ctx) => s === [...s].reverse().join("") || ctx.mustBe("a palindrome")
])

// ArkErrors: must be a palindrome (was "arktype")
Palindrome("arktype")
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
const Palindrome = type(
	"string",
	":",
	(s, ctx) => s === [...s].reverse().join("") || ctx.mustBe("a palindrome")
)

// ArkErrors: must be a palindrome (was "arktype")
Palindrome("arktype")
```

    </SyntaxTab>

</SyntaxTabs>

`ctx.reject()` can also set the error's `path` and `actual`, e.g. to report a mismatch at the right key without printing a password:

```ts
const Form = type({
	password: "string",
	confirmPassword: "string"
}).narrow(
	(data, ctx) =>
		data.password === data.confirmPassword ||
		ctx.reject({
			expected: "identical to password",
			actual: "",
			path: ["confirmPassword"]
		})
)

// ArkErrors: confirmPassword must be identical to password
Form({ password: "arktype", confirmPassword: "artkype" })
```

If a narrow's return type is a type predicate, the `Type` infers it:

```ts
// Type<`ark${string}`>
const ArkString = type("string").narrow(
	(data, ctx): data is `ark${string}` =>
		data.startsWith("ark") || ctx.reject("a string starting with 'ark'")
)
```

The [traversal API](/docs/traversal-api) documents everything `ctx` can do.

## Filter

`filter` is like `narrow`, but checks a type's **input** instead of its output. The difference matters when the type transforms its input:

- **`narrow`** checks the **output**, after morphs run
- **`filter`** checks the **input**, before morphs run

```ts
const ShortNumeric = type("string.numeric.parse").filter(
	// s is the input string, not the parsed number
	(s, ctx) => s.length <= 10 || ctx.reject("at most 10 characters")
)

// 123
ShortNumeric("123")

// ArkErrors: must be at most 10 characters (was "12345678901")
ShortNumeric("12345678901")
```

Like `narrow`, a type predicate returned by a filter is inferred, here as the type's input.

## Pipe

A pipe transforms data after it is validated, through one or more functions called **morphs**. The [intro](/docs/intro/morphs-and-more) walks through examples.

<SyntaxTabs>
	<SyntaxTab fluent>

```ts
// Type<(In: string) => Out<string>>
const TrimStart = type("string").pipe(str => str.trimStart())
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
// Type<(In: string) => Out<string>>
const TrimStart = type(["string", "=>", str => str.trimStart()])
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
// Type<(In: string) => Out<string>>
const TrimStart = type("string", "=>", str => str.trimStart())
```

    </SyntaxTab>

</SyntaxTabs>

A morph receives the validated value itself rather than a copy, so a morph that mutates its argument mutates the caller's data. ArkType's own transforms, like defaults, copy each object they change and share every untransformed value with the input, and input nothing transforms is returned as is. The exception is an instance of a builtin class, like a `Date`, `Map` or function, which keeps its state in internal slots and is transformed in place. [`mutatesInput`](/docs/configuration#mutatesinput) writes transforms into the data instead.

```ts
const T = type({ a: "string.trim", b: { c: "string" } })
const input = { a: " x ", b: { c: "y" } }

const out = T.assert(input)

out === input // false
out.b === input.b // true
```

### To

A morph can return `ArkErrors` to fail validation, so a `Type` works as a morph: it validates the previous output. The `to` operator pipes to a definition without wrapping it in `type`:

<SyntaxTabs>
	<SyntaxTab string>

```ts
// Type<(In: string) => To<number>>
const ParseEven = type("string.numeric.parse |> number % 2")

// ArkErrors: must be even (was 3)
ParseEven("3")
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// Type<(In: string) => To<number>>
const ParseEven = type("string.numeric.parse").to("number % 2")

// ArkErrors: must be even (was 3)
ParseEven("3")
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
// Type<(In: string) => To<number>>
const ParseEven = type(["string.numeric.parse", "|>", "number % 2"])

// ArkErrors: must be even (was 3)
ParseEven("3")
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
// Type<(In: string) => To<number>>
const ParseEven = type("string.numeric.parse", "|>", "number % 2")

// ArkErrors: must be even (was 3)
ParseEven("3")
```

    </SyntaxTab>

</SyntaxTabs>

`.to("number % 2")` is the same as `.pipe(type("number % 2"))`.

<AnchorAliases pipe-n-ary />
### n-ary

`.pipe()` accepts any number of morphs and types. `type.pipe()` does the same without a `Type` to start from:

```ts
// Type<(In: string) => To<string>>
const TrimStartNonEmpty = type.pipe(
	type.string,
	s => s.trimStart(),
	type.string.atLeastLength(1)
)

// ArkErrors: must be non-empty
TrimStartNonEmpty("   ")
```

## valueOf

`type.valueOf` allows the values of a TypeScript `enum` or an enum-like object:

```ts
enum TsEnum {
	numeric = 1
}

// Type<TsEnum.numeric>
const EnumType = type.valueOf(TsEnum)
```

It is almost the same as `type.enumerated(...Object.values(o))`. The difference is an entry whose key is another entry's numeric value, mapping back to that entry's key. That's how TypeScript compiles a numeric `enum`, so `valueOf` skips the reverse entry:

```ts
// what TsEnum compiles to
const equivalentObject = {
	numeric: 1,
	"1": "numeric"
} as const

// allows only 1, though it infers Type<1 | "numeric">
const EquivalentType = type.valueOf(equivalentObject)
```

<Callout type="info" title="Prefer enumerated">

TypeScript is moving away from features that emit JavaScript, like `enum`, which [`--erasableSyntaxOnly`](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly) disallows. `type.valueOf` is for code that already uses `enum`. Otherwise, list values with [`type.enumerated`](/docs/expressions#enumerated) or a literal union.

</Callout>

## fn

`type.fn` wraps a function so its parameters, and optionally its return value, are validated when it's called. Parameters use tuple syntax. Put a return type after `":"`.

```ts
// @errors: 2345
const len = type.fn("string | unknown[]", ":", "number")(s => s.length)

len("foo") // 3
len([1, 2]) // 2

// TraversalError: value at [0] must be a string or an array (was boolean)
len(true)
```

The result is a `TypedFn`, which is introspectable:

```ts
const len = type.fn("string | unknown[]", ":", "number")(s => s.length)

len.expression // "(string | Array) => number"
len.params.expression // "[string | Array]"
len.returns.expression // "number"
```

Parameters can be defaultable, optional or variadic:

```ts
const greet = type.fn("string = 'world'")(name => `Hello, ${name}!`)

greet() // "Hello, world!"

const join = type.fn("...", "string[]")((...parts) => parts.join(","))

join("a", "b") // "a,b"
```

Without a return type, the return type is inferred from the implementation and not validated.

## Meta

Metadata attaches information to a type. ArkType reads some of it, like `description`, which error messages use. You can read the rest from the type's `meta`.

<SyntaxTabs>
	<SyntaxTab fluent>

```ts
const SpecialString = type("string").configure({
	description: "a special string"
})

// .describe() is shorthand for a description
const SpecialNumber = type("number").describe("a special number")

// ArkErrors: must be a special number (was a string)
SpecialNumber("five")
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const SpecialString = type([
	"string",
	"@",
	{
		description: "a special string"
	}
])

// a string is shorthand for a description
const SpecialNumber = type(["number", "@", "a special number"])

// ArkErrors: must be a special number (was a string)
SpecialNumber("five")
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
const SpecialString = type("string", "@", {
	description: "a special string"
})

// a string is shorthand for a description
const SpecialNumber = type("number", "@", "a special number")

// ArkErrors: must be a special number (was a string)
SpecialNumber("five")
```

    </SyntaxTab>

</SyntaxTabs>

An object definition can hold its own metadata under an `"@"` key:

```ts
const User = type({
	"@": "a user",
	name: "string"
})

// ArkErrors: must be a user (was a number)
User(5)
```

A configured description, like any message you configure, takes precedence over the [locale](/docs/i18n#your-own-messages), so it isn't translated.

The `keyword` key is reserved: built-in keywords set `meta.keyword` to their name so a locale can find their phrase, and configuring a description removes it. Name your own metadata something else.

To configure only some of a type's nodes, pass a selector after the metadata:

<SyntaxTabs>
	<SyntaxTab fluent>

```ts
const Point = type({
	x: "number",
	y: "number"
}).configure(
	{ description: "a coordinate" },
	// every domain node: the object and both numbers
	"domain"
)

// ArkErrors: x must be a coordinate (was a string)
Point({ x: "1", y: 2 })
```

    </SyntaxTab>

    <SyntaxTab tuple>

```ts
const Point = type([
	{
		x: "number",
		y: "number"
	},
	"@",
	{ description: "a coordinate" },
	// every domain node: the object and both numbers
	"domain"
])

// ArkErrors: x must be a coordinate (was a string)
Point({ x: "1", y: 2 })
```

    </SyntaxTab>

    <SyntaxTab args>

```ts
const Point = type(
	{
		x: "number",
		y: "number"
	},
	"@",
	{ description: "a coordinate" },
	// every domain node: the object and both numbers
	"domain"
)

// ArkErrors: x must be a coordinate (was a string)
Point({ x: "1", y: 2 })
```

    </SyntaxTab>

</SyntaxTabs>

Selectors are documented with [`select`](/docs/internals/nodes#select).

## Cast

A cast changes how a `Type` is inferred without changing what it validates:

<SyntaxTabs>
	<SyntaxTab string>

```ts
// any string, but the editor suggests "foo" and "bar"
type AutocompletedString = "foo" | "bar" | (string & {})

const MyObj = type({
	autocompletedString: "string" as type.cast<AutocompletedString>
})
```

    </SyntaxTab>

    <SyntaxTab fluent>

```ts
// any string, but the editor suggests "foo" and "bar"
type AutocompletedString = "foo" | "bar" | (string & {})

const MyObj = type({
	autocompletedString: type.string.as<AutocompletedString>()
})
```

    </SyntaxTab>

</SyntaxTabs>

## Parenthetical

Operators have the same precedence as in TypeScript, and parentheses group them the same way:

```ts
// Type<{ stringOrNumbers: string | number[]; stringsOrNumbers: (string | number)[] }>
const Groups = type({
	stringOrNumbers: "string | number[]",
	stringsOrNumbers: "(string | number)[]"
})
```

## this

`this` references the root of the definition it's in, which makes the type recursive:

```ts
const DisappointingGift = type({
	label: "string",
	"box?": "this"
})

const out = DisappointingGift({
	label: "foo",
	box: { label: "bar", box: {} }
})

if (out instanceof type.errors) {
	// ArkErrors: box.box.label must be a string (was missing)
	console.error(out.summary)
} else {
	// narrowed inference to arbitrary depth
	console.log(out.box?.box?.label)
	//                         ^?
}
```

In a scope, `this` is a `ParseError`. Reference the alias by name instead, as described in [cyclic types](/docs/scopes#cyclic-types):

```ts
const types = scope({
	DisappointingGift: {
		label: "string",
		"box?": "DisappointingGift"
	}
}).export()
```
