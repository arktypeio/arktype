# @ark/aot

## 0.0.1

Initial release: constructs arktype definitions at build time, so arktype's parser never ships (#810). It runs as a bundler plugin, as Node, Bun and Turbopack drivers, as `arktype-precompile --check`, as `arktype-precompile --emit` over what `tsc` emits and as an ESLint rule, and `arktype-precompile --declare` emits declarations sharing one file of shapes. See the [README](./README.md).

With `optimize: "size"`, as the `"smallest"` preset sets, and detailed errors, a build writes each node as a call to a small runtime checker that describes what it checks from its rule, and each site creates its validator in place. A module whose Types are too few to pay for the checkers' runtime is compiled instead. A Type configured with a `message`, like a form's field, is the checker of what it checks saying that message, at each of its sites and where its key is missing, so fields checking the same thing share one checker. A production bundle built with `optimize` unset whose validators, compiled, would outweigh the arktype they replace is written as `optimize: "size"` writes it where a browser loads it, with a warning, and only warns, naming the `"smallest"` preset, where the build can't tell what loads it, as with Turbopack.

A validator's errors read as its Type's do: each `message`, `expected` and `summary`, the alternatives a union lists and the message `assert` throws are the text arktype writes, as a missing key's ` (was missing)` and a `pipe.try` morph's `(SyntaxError: ...)` are, and neither writes what a value was unless `actual` is configured. A validator's error has no `actual`, though a configured `message` writer reads `actual` as arktype's does.

A production webpack or Rspack build, Next.js's webpack compilers among them, writes the same validators as an esbuild build: it builds its modules as they are, reads them, so it reads what its resolver, loaders and generated entries make of them, then builds again those it writes. It reads each module again as the loaders after its own built it, as Babel's where Next finds a Babel config, and fails where that reads what it left out, naming the module, the read and the loaders, or the loader compiling a module to CommonJS, whose reads it can't follow. A build it can't read builds each module on its own, with a warning. It reads the modules Next.js's `optimizePackageImports` builds a listed package's entry as, one for each set of names imported from it, as that entry's file, so a Next.js app listing its workspace packages there is still read whole. An `import()` of a computed specifier loads one of the modules the bundler built for the files it can name, so it keeps each member only where one of those exports a validator. A definition reading a value code the build doesn't follow may write, as what a package tsc built to CommonJS shares between its modules, is precompiled, and its validator checks the value as it's created, a list or enum read whole by a digest of its keys and values. It reads a TypeScript enum as a loader's TypeScript transform writes it. A Vite, Rollup or Rolldown build can't see a read a plugin adds after its transform, which a pruned build may have left out: list such a plugin ahead of `precompile.vite()` with `enforce: "pre"`, or set `prune: false`.

`next build` with Turbopack reads its project before it writes a module, as Turbopack's loader sees one module at a time and can serve only what's on disk: export next.config through `withPrecompile` from `@ark/aot/turbopack`. Each process of its pool answers from one read, its validators held once in files under `node_modules/.bin/.ark`, so a route's first load and its server output no longer grow with what each module would hold of its own. Each module is checked in each layer against what the read saw, and fails where it differs. It reads as `withPrecompile` has Next load `next.config`, before Turbopack starts, writing only what changed, so Turbopack's build cache keeps from an earlier build only what the read left as it was. It reads each route, under app/build/ or app/.well-known/ too, every script under pages/ and what a link leads to, as Next routes them. Where the project can't be read, as where a Babel config or `experimental.swcPlugins` has Turbopack transform a module after the loader, it warns, and each module holds its own validators. Turbopack aliases `@ark/schema/runtime` to `@ark/aot/turbopack/runtime`, which the loader writes as the copy of @ark/schema's runtime the build's options load, so the aliases stay alike as the options change: Next 16.4.1 hangs a cached build past an alias removed since.

A build keeps each answer it can reuse in `node_modules/.cache/ark` where it runs, so a later build, dev server or Next process reads it while nothing that decided it changed: the module, each file the precompiler read and what each import resolved to, the options, and the precompiler's own code and Node. A watch build keeps its precompiler across changes, analyzing again only the modules a change reaches, and stores only what it answered before the first.

With `jsonInput: true`, a build trusts the objects it checks to be plain data, as `JSON.parse` returns, so a Type rejecting undeclared keys counts a plain object's keys rather than checking each. On moltar's benchmark, it takes 0.82x a default build's cycles on parseStrict and 0.71x on assertStrict, level with ata's ahead-of-time build on parseStrict and 0.88x its cycles on assertStrict. Data with a declared key held non-enumerable can then pass with an undeclared key, as the options page shows.

A validator bakes `expression`, `description`, `json`, `toJSON`, `toJsonSchema` and `~standard.jsonSchema` only where the build follows it to code reading them, its dependencies' included, so the MCP SDK, the AI SDK, Elysia's OpenAPI plugin, hono-openapi and oRPC's converter get a JSON Schema with no `members` set, and one only validated bakes none. A build reading one module at a time, like webpack or Turbopack, bakes what each module reads of a validator it imports where it reads it. A validator stored at an object's key is followed past the helpers tsc and SWC declare in a module they emit as CommonJS, like `__createBinding` and `_interop_require_wildcard`, which read a module's exports alone, so a workspace package built to CommonJS doesn't have the build lose track of each by them. Reading one a validator lacks throws, naming the member and the setting, or reads `undefined` where a production bundle left out the validator's methods, which no bundle does where a `define` names a binding or, on webpack and Rspack, a loader after arktype's adds a read of one.
